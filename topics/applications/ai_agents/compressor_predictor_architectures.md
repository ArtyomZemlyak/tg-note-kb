# Архитектуры Compressor-Predictor в агентных системах

## Обзор

Архитектура Compressor-Predictor — это подход к проектированию агентных систем, при котором процесс генерации ответа разделяется на два этапа: сжатие информации (compressor) и генерация финального ответа (predictor). Этот подход особенно полезен для преодоления ограничений по контекстному окну и вычислительным бюджетам в сложных агентных системах.

## Определение архитектуры

В архитектуре Compressor-Predictor:
- **Компрессор** (Compressor): модель, которая принимает исходный контекст X (сырые данные, документы, результаты поиска) и создает краткое саммари Z
- **Предиктор** (Predictor): модель, которая принимает саммари Z и генерирует финальный ответ Y

Математически это представляется как цепочка Маркова: **X → Z → Y**, где:
- X — исходный контекст (сырые данные)
- Z — сжатое саммари (output от компрессора)
- Y — финальный ответ (output от предиктора)

## Теоретико-информационный подход

Согласно статье "An Information Theoretic Perspective on Agentic System Design", архитектуру Compressor-Predictor можно анализировать с точки зрения теории информации:

### Взаимная информация (Mutual Information, MI)

Качество компрессора измеряется через взаимную информацию I(X; Z) между исходным контекстом и саммари. Это показывает, насколько информации сохраняется в процессе сжатия.

### Information Rate

Определение: взаимная информация на токен. Это универсальная метрика битовой эффективности, не зависящая от конкретной downstream задачи.

## Преимущества архитектуры

### 1. Эффективность использования контекста
- Компрессор концентрирует наиболее важную информацию в компактном виде
- Предиктор работает с более управляемым объемом данных
- Уменьшается вероятность "потери сигнала" в длинных контекстах

### 2. Экономия вычислительных ресурсов
- Возможно использование более легкого предиктора, который работает быстрее
- Компрессор может работать асинхронно или на менее мощных устройствах (edge computing)
- Снижение стоимости API-вызовов (особенно при использовании дорогих LLM на стороне предиктора)

### 3. Модульность и настраиваемость
- Каждый компонент может быть оптимизирован независимо
- Возможность замены одного компонента без перестройки всей системы
- Гибкость в распределении вычислений между edge и cloud

## Применения

### RAG-системы
- Компрессор: обрабатывает извлеченные документы, создавая краткие саммари
- Предиктор: генерирует ответ на основе саммари и запроса пользователя
- Пример: Apple CLaRa (Continuous Latent Reasoning), который использует непрерывное латентное пространство для сжатия документов

### Multi-step агентные системы
- Компрессор: суммирует результаты промежуточных шагов и инструментов
- Предиктор: принимает решения и генерирует финальный ответ
- Позволяет агенту управлять длинными цепочками рассуждений

### Edge-cloud архитектуры
- Edge компрессор: обрабатывает локальные данные, сохраняя конфиденциальность
- Cloud предиктор: использует мощные модели для генерации ответов
- Пример: локальный 3B-компрессор + облачный предиктор

## Оптимизация архитектуры

### Масштабирование компрессора vs. предиктора

Согласно теоретико-информационному анализу:
- **Масштабирование компрессора** дает значительно больший прирост точности (до 60% при увеличении с 1B до 7B)
- **Масштабирование предиктора** дает ограниченный прирост (всего 12% при увеличении с 70B до 405B)

**Вывод:** инвестиции должны быть направлены в первую очередь в компрессор, а не в предиктор.

### Information Rate как метрика качества

Вместо оценки по downstream точности, компрессор можно оптимизировать независимо, используя:
- Взаимную информацию I(X; Z) как меру сохранения информации
- Information Rate как универсальную метрику эффективности

## Связь с другими подходами

### Сравнение с end-to-end подходами

- **End-to-end**: весь контекст подается в одну модель
- **Compressor-Predictor**: разделение задачи между двумя специализированными моделями
- Compressor-Predictor часто превосходит end-to-end при меньших вычислительных затратах

### Интеграция с existing агентными системами

- Может быть интегрирована в существующие фреймворки (Agentic-Flow, LangGraph и др.)
- Добавляет уровень абстракции для управления контекстом
- Совместима с различными механизмами внимания и retrieval

## Примеры реализации

### Apple CLaRa
- Использует компрессор для сжатия документов в 16-128 раз
- Встроенный Query Reasoner как предиктор
- Объединяет извлечение и генерацию в непрерывном латентном пространстве

### Deep Research системы
- Компрессор: обрабатывает результаты поиска и документов
- Предиктор: генерирует финальный исследовательский ответ
- Возможность масштабирования каждого компонента независимо

## Ограничения и проблемы

### Проблема атрибуции
- Когда агент ошибается, сложно определить: ошибка компрессора (потеря информации) или предиктора (неправильная интерпретация)
- Требуется метрика качества сжатия, независимая от downstream задачи

### Зависимость предиктора от качества сжатия
- Предиктор не может "восстановить" информацию, потерянную компрессором
- "Garbage in, garbage out" принцип применяется к архитектуре

### Сложность координации
- Необходимость синхронизации между двумя моделями
- Дополнительная задержка от процесса сжатия
- Возможные проблемы с консистентностью и устареванием данных

## Будущие направления

### Автоматическая оптимизация архитектуры
- Использование Information Rate для автоматической настройки размера саммари
- Динамическое распределение вычислительных ресурсов между компрессором и предиктором

### Интеграция с другими паттернами
- Соединение с механизмами memory в агентных системах
- Сочетание с multi-expert и MoE подходами
- Интеграция с reinforcement learning для адаптивного сжатия
