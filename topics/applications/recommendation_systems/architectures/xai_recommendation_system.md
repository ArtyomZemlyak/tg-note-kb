# Рекомендательная система xAI (X/Twitter)

## Описание

Рекомендательная система xAI представляет собой открытую реализацию алгоритма, который управляет лентой "For You" на платформе X (бывший Twitter). Система была опубликована в опенсорс и основана на трансформерной архитектуре с минимальным количеством эвристических решений и ручного feature engineering'а.

## Архитектура

Система следует многоступенчатой архитектуре:

1. **Home Mixer** - оркестратор, который координирует весь процесс
2. **Thunder** - контент из сети (посты от аккаунтов, на которые вы подписаны)
3. **Phoenix** - ML-система для контента вне сети (поиск и ранжирование)
4. **Кандидатская цепочка (Candidate Pipeline)** - фреймворк для построения рекомендательных пайплайнов

## Компоненты системы

### Phoenix (Основной ML компонент)

Phoenix использует двухступенчатый рекомендательный пайплайн:

#### 1. Поиск (Двухбашенная модель)

- **User Tower**: кодирует особенности пользователя и историю взаимодействий в эмбеддинг
- **Candidate Tower**: кодирует все посты в эмбеддинги
- **Поиск по схожести**: извлекает топ-K постов по скалярному произведению схожести

#### 2. Ранжирование (Трансформер с изоляцией кандидатов)

- Предсказывает вероятности взаимодействия для каждого кандидата
- Принимает историю пользователя и пост-кандидаты в качестве входных данных
- Использует специальную маску внимания, чтобы кандидаты не могли обращаться друг к другу
- Выводит вероятности для каждого типа действия (лайк, ответ, репост и т.д.)

### Home Mixer

- Функционирует как уровень оркестрации
- Использует фреймворк CandidatePipeline со стадиями:
  - Query Hydrators: загрузка контекста пользователя (история взаимодействий, список подписок)
  - Источники: извлечение кандидатов из Thunder и Phoenix
  - Hydrators: наполнение кандидатов дополнительными данными
  - Фильтры: удаление неподходящих кандидатов
  - Scorers: предсказание взаимодействия и вычисление итоговых оценок
  - Selector: сортировка по оценке и выбор топ K
  - Post-Selection Filters: финальные проверки видимости и удаление дубликатов

### Thunder

- Построен как хранилище постов и пайплайн реального времени
- Ключевые обязанности:
  - Потребление событий создания/удаления постов из Kafka
  - Поддержка пользовательских хранилищ для оригинальных постов, ответов/репостов и видео
  - Обслуживание "внутрисетевых" кандидатов постов от аккаунтов, на которые подписан пользователь
  - Автоматический отсев постов старше периода удержания

## Технические характеристики

### Стадии пайплайна

1. Наполнение запроса: загрузка истории недавних взаимодействий пользователя и метаданных
2. Поиск кандидатов: из Thunder (внутрисетевые) и Phoenix Поиск (внешнесетевые)
3. Наполнение кандидатов: пополнение данными о посте, авторе, медиа и т.д.
4. Фильтрация до оценки: удаление дубликатов, старых постов, заблокированного контента и т.д.
5. Оценка: применение нескольких оценщиков последовательно
6. Выбор: сортировка по оценке и выбор топ кандидатов
7. Пост-обработка выбора: финальная проверка

### Оценка и ранжирование

Модель трансформера на основе Grok предсказывает вероятности для нескольких типов взаимодействий:
- P(favorite), P(reply), P(repost), P(quote)
- P(click), P(profile_click), P(video_view), P(photo_expand)
- P(share), P(dwell), P(follow_author)
- P(not_interested), P(block_author), P(mute_author), P(report)

Взвешенный оценщик объединяет их в итоговую оценку:
Итоговая оценка = Σ (вес_i × P(действие_i))

Положительные действия имеют положительные веса, отрицательные действия - отрицательные веса.

### Стратегия фильтрации

Две стадии фильтрации:

Фильтрация до оценки:
- DropDuplicatesFilter
- CoreDataHydrationFilter
- AgeFilter
- SelfpostFilter
- RepostDeduplicationFilter
- IneligibleSubscriptionFilter
- PreviouslySeenPostsFilter
- MutedKeywordFilter
- AuthorSocialgraphFilter

Фильтры после выбора:
- VFFilter (удаленные/спам/насилие/кровь)
- DedupConversationFilter

## Ключевые решения по дизайну

1. **Без ручных признаков**: полностью полагается на трансформерную модель Grok для изучения релевантности из последовательностей взаимодействий пользователя

2. **Изоляция кандидатов при ранжировании**: во время вывода трансформера, кандидаты не могут обращаться друг к другу - только к контексту пользователя, обеспечивая постоянные и кешируемые оценки

3. **Хэш-базированные эмбеддинги**: и поиск, и ранжирование используют несколько функций хэширования для поиска по эмбеддингам

4. **Предсказание множества действий**: предсказывает вероятности для многих действий вместо одной оценки релевантности

5. **Композиционная архитектура пайплайна**: фреймворк candidate-pipeline предоставляет гибкую структуру с разделением ответственности

## Реализация на практике

- Реализация трансформера адаптирована из открытой версии Grok-1 от xAI
- Адаптирована для использования в рекомендательных системах
- Использует специальную маску внимания в трансформере для достижения изоляции кандидатов
- Распределение языка: 62.9% Rust, 37.1% Python
- Практически устранены все ручные признаки и эвристики

## Интеграция источников

Система сочетает два источника:
1. Внутрисетевые (Thunder): посты от аккаунтов, на которые вы подписаны
2. Внешнесетевые (Phoenix Поиск): посты, обнаруженные из глобального корпуса

Оба источника объединяются и ранжируются с использованием трансформерной модели Phoenix

## Архитектура трансформера

Архитектура трансформера по умолчанию (видны роторные эмбеддинги, rmsnorm) и является форком Grok. Предобученный Grok не используется, только код. В тестах и конфигах указаны очень маленькие размеры трансформера (вроде два слоя и скрытый размер 128). Длина используемой истории пользователя в конфигах - то ли 128, то ли 32 (в разных местах по-разному написано). Одинаковая архитектура трансформера используется как для ранжирования, так и для генерации кандидатов.

## Кодирование сущностей

Для кодирования сущностей (постов, авторов, пользовательских признаков) используется multi-hash lookup: делают что-то типа linear(concat(embedding(hash1), embedding(hash2))). В конфигах везде указаны num_hashes=2, то есть по два лукапа на сущность. Для разных признаков используются раздельные таблицы эмбеддингов (в унифицированном подходе была бы одна общая); то есть для авторов, постов, пользователей - разные таблицы. Эмбеддинг события в истории пользователя формируется на основе поста, автора, рекомендательной поверхности и действия пользователя.

Еще как будто берут мультихэши от айдишника пользователя и подают в трансформер вместе с историей пользователя.

## Генерация кандидатов

Башня кандидата в двухбашенном трансформере для генерации кандидатов очень простая - Linear(SiLU(Linear)). 

## Ранжирование

Ранжирующий трансформер устроен таким образом, что токены истории+пользователя видят только токены истории+пользователя, а каждый кандидат видит себя и токены истории+пользователя (кастомная маска внимания). Подают сразу несколько кандидатов, но работает это эквивалентно тому, как если бы отдельно прогнали трансформер для каждого кандидата, добавляя его в конец последовательности.

## Multi-action предсказание

Трансформер предсказывает вероятности сразу для кучи разных сигналов (like, reply, click, repost - полный список в репозитории). Для финального ранжирования, эти вероятности суммируются с весами в единый скор (но как подбираются веса - не пишут). Такую схему использовали и в прошлой ранжирующей нейросети, но только теперь эти вероятности приходят напрямую из трансформера.

## Проецирование "Феникс"

Интересно отметить, что всю эту трансформерную поделку в xAI решили назвать "Феникс". Ранее в Яндексе также инициировали похожий проект по упрощению ранжирования в единую нейросеть с трансформером, и тоже назвали её Фениксом.
