# Итеративный пайплайн внедрения LLM в рекомендательные системы для Production

## Обзор

Данный документ описывает **поэтапный итеративный подход** к внедрению больших языковых моделей (LLM) в промышленные рекомендательные системы. Каждая итерация представляет собой законченный этап, который может быть развернут в production независимо, что позволяет минимизировать риски и постепенно наращивать сложность системы.

Основная идея: начинать с наименее рискованных изменений и постепенно переходить к более сложным архитектурам, получая ценность на каждом этапе.

## Принципы итеративного внедрения

1. **Минимальный риск**: Начинать с изменений, не влияющих на онлайн-инференс
2. **Измеримость**: Каждая итерация должна иметь четкие метрики успеха
3. **Возможность отката**: Любое изменение должно быть легко откатить
4. **Накопление знаний**: Каждая итерация готовит инфраструктуру для следующей
5. **Баланс качество/производительность**: Постепенное усложнение архитектуры

## Итерация 1: LLM для офлайн-инженерии признаков

**Уровень риска:** Минимальный  
**Время внедрения:** 2-4 недели  
**Влияние на production:** Отсутствует (офлайн-процессы)

### Цель

Использовать LLM для обогащения признаков пользователей и предметов без изменения онлайн-пайплайна рекомендаций.

### Архитектура

```
┌─────────────────┐      ┌──────────────┐      ┌─────────────────┐
│  Исходные данные │ ────►│  LLM (офлайн) │ ────►│  Обогащенные    │
│  (предметы,     │      │  (Batch API) │      │  признаки в     │
│   пользователи) │      │              │      │  Feature Store  │
└─────────────────┘      └──────────────┘      └─────────────────┘
                                                        │
                                                        ▼
                                               ┌─────────────────┐
                                               │  Существующая   │
                                               │  модель RecSys  │
                                               │  (без изменений)│
                                               └─────────────────┘
```

### Задачи LLM

1. **Генерация тегов для предметов**:
   - Анализ описаний предметов и генерация дополнительных тегов
   - Категоризация предметов по иерархической таксономии
   - Выявление скрытых атрибутов (например, "подходит для подарка")

2. **Аугментация пользовательских профилей**:
   - Суммаризация истории взаимодействий
   - Извлечение интересов из поведения пользователя
   - Создание текстовых описаний предпочтений

3. **Обогащение метаданных**:
   - Генерация описаний для предметов без описаний
   - Извлечение сущностей (NER) из текстов
   - Сентимент-анализ отзывов и ревью

### Техническая реализация

```python
# Пример пайплайна для генерации тегов
from llm_client import LLMClient

class ItemTagGenerator:
    def __init__(self, llm_model="gpt-4o-mini"):
        self.llm = LLMClient(model=llm_model)
        self.prompt_template = """
        Проанализируй описание предмета и сгенерируй 5-10 релевантных тегов.
        
        Название: {title}
        Описание: {description}
        Категория: {category}
        
        Теги (через запятую):
        """
    
    def generate_tags(self, item_data):
        prompt = self.prompt_template.format(**item_data)
        response = self.llm.generate(prompt)
        return self._parse_tags(response)
    
    def batch_process(self, items, batch_size=100):
        """Офлайн обработка каталога"""
        enriched_items = []
        for batch in self._chunk(items, batch_size):
            enriched = self._process_batch(batch)
            enriched_items.extend(enriched)
        return enriched_items
```

### Метрики успеха

- **Качество тегов**: Precision/Recall через оценку аннотаторами
- **Покрытие**: % предметов с обогащенными признаками
- **Влияние на RecSys**: A/B тест с новыми признаками (CTR, конверсия)

### Преимущества

- ✅ Нет влияния на latency онлайн-системы
- ✅ Легкий откат (просто не использовать новые признаки)
- ✅ Быстрое получение ценности
- ✅ Накопление данных для следующих итераций

### Риски и ограничения

- ⚠️ Стоимость LLM API для больших каталогов
- ⚠️ Качество генерации может варьироваться
- ⚠️ Необходимость валидации сгенерированных признаков

```python
class DataAugmentationPipeline:
    def __init__(self, llm_model="gpt-4o"):
        self.llm = LLMClient(model=llm_model)
    
    def generate_hard_negatives(self, user_history, positive_items):
        """Генерация сложных негативных примеров"""
        prompt = f"""
        Пользователь взаимодействовал с этими предметами:
        {self._format_items(user_history)}
        
        Сгенерируй 5 предметов, которые похожи на позитивные,
        но пользователь с ними НЕ взаимодействовал (hard negatives):
        Позитивные: {self._format_items(positive_items)}
        
        Hard negatives:
        """
        return self.llm.generate(prompt)
    
    def create_synthetic_interactions(self, user_profiles, item_catalog):
        """Генерация синтетических взаимодействий для cold-start"""
        # Генерация для новых пользователей
        synthetic_users = self._generate_new_user_profiles()
        # Генерация для новых предметов
        synthetic_items = self._generate_new_item_interactions()
        return synthetic_users, synthetic_items
```

### Метрики успеха

- **Качество данных**: Оценка синтетических данных аннотаторами
- **Влияние на модель**: Улучшение offline-метрик (NDCG, HitRate)
- **Coverage**: Улучшение рекомендаций для long-tail предметов

### Преимущества

- ✅ Улучшение качества модели без изменения архитектуры
- ✅ Решение проблемы cold-start
- ✅ Балансировка данных для редких классов

## Итерация 3: LLM как энкодер признаков (офлайн/near-line)

**Уровень риска:** Средний  
**Время внедрения:** 4-8 недель  
**Влияние на production:** Минимальное (офлайн-эмбеддинги)

### Цель

Заменить традиционные эмбеддинги предметов и пользователей на представления, полученные от LLM.

### Архитектура

```
┌─────────────────┐      ┌──────────────┐      ┌─────────────────┐
│  Текстовые      │ ────►│  LLM         │ ────►│  LLM            │
│  описания       │      │  (Encoder)   │      │  Embeddings     │
│  (предметы,     │      │              │      │  (векторное     │
│   пользователи) │      │              │      │   хранилище)    │
└─────────────────┘      └──────────────┘      └─────────────────┘
                                                        │
                                                        ▼
                                               ┌─────────────────┐
                                               │  Существующая   │
                                               │  модель (с новыми
                                               │  эмбеддингами)  │
                                               └─────────────────┘
```

### Подходы

#### 3.1 Использование готовых LLM-эмбеддингов

- Извлечение эмбеддингов из предобученных моделей (BERT, RoBERTa, E5)
- Fine-tuning на доменных данных
- Использование моделей типа U-BERT, UNBERT

#### 3.2 Контрастивное обучение с LLM

- Обучение с InfoNCE loss
- Использование In-Batch негативов и Hard Negatives
- Matryoshka learning для сжатия эмбеддингов

#### 3.3 Кросс-доменные представления

- Унифицированные эмбеддинги для нескольких доменов
- Zero-shot transfer между доменами
- Подходы типа ZESRec, UniSRec

### Техническая реализация

```python
class LLMFeatureEncoder:
    def __init__(self, encoder_model="intfloat/e5-large-v2"):
        self.encoder = AutoModel.from_pretrained(encoder_model)
        self.tokenizer = AutoTokenizer.from_pretrained(encoder_model)
    
    def encode_items(self, items, batch_size=256):
        """Создание эмбеддингов для предметов"""
        texts = [self._format_item(item) for item in items]
        embeddings = []
        
        for batch in self._chunk(texts, batch_size):
            inputs = self.tokenizer(
                batch, 
                padding=True, 
                truncation=True, 
                return_tensors="pt",
                max_length=512
            )
            
            with torch.no_grad():
                outputs = self.encoder(**inputs)
                batch_embeddings = outputs.last_hidden_state[:, 0, :]  # CLS token
                embeddings.append(batch_embeddings)
        
        return torch.cat(embeddings).numpy()
    
    def _format_item(self, item):
        """Форматирование предмета для кодирования"""
        return f"Title: {item['title']}. Description: {item['description']}"
```

### Метрики успеха

- **Качество эмбеддингов**: Визуализация (t-SNE), кластеризация
- **Offline-метрики**: NDCG@K, HitRate@K, MRR
- **Online-метрики**: CTR, время сессии, конверсия

### Преимущества

- ✅ Более богатые семантические представления
- ✅ Лучшая работа с cold-start предметами
- ✅ Возможность кросс-доменных рекомендаций

### Риски и ограничения

- ⚠️ Увеличение времени предобработки
- ⚠️ Необходимость хранения больших эмбеддингов
- ⚠️ Возможное ухудшение на специфичных доменах

## Итерация 4: LLM для ранжирования (near-line/онлайн)

**Уровень риска:** Средне-высокий  
**Время внедрения:** 6-12 недель  
**Влияние на production:** Влияние на latency (требует оптимизации)

### Цель

Использовать LLM для финального ранжирования кандидатов, учитывая сложный контекст и персонализацию.

### Архитектура

```
┌─────────────────┐      ┌──────────────┐      ┌─────────────────┐
│  Candidate      │ ────►│  LLM         │ ────►│  Финальное      │
│  Generation     │      │  (Ranking)   │      │  ранжирование   │
│  (традиционная) │      │              │      │                 │
└─────────────────┘      └──────────────┘      └─────────────────┘
                                │
                                ▼
                       ┌─────────────────┐
                       │  Контекст:      │
                       │  - Пользователь │
                       │  - Сессия       │
                       │  - Предметы     │
                       └─────────────────┘
```

### Подходы

#### 4.1 Pointwise ранжирование

- Оценка каждого предмета независимо
- Формат: "Оцени релевантность предмета X пользователю Y от 1 до 5"
- Быстрее, но игнорирует относительные предпочтения

#### 4.2 Listwise ранжирование

- Одновременная оценка списка предметов
- Формат: "Отранжируй эти предметы по релевантности"
- Лучше учитывает относительные предпочтения

#### 4.3 Pairwise ранжирование

- Сравнение пар предметов
- Формат: "Какой предмет более релевантен: A или B?"
- Требует больше инференсов, но точнее

### Техническая реализация

```python
class LLMRanker:
    def __init__(self, model="gpt-4o-mini", cache_enabled=True):
        self.llm = LLMClient(model=model)
        self.cache = EmbeddingCache() if cache_enabled else None
    
    def rank_candidates(self, user_context, candidates, top_k=10):
        """Ранжирование кандидатов"""
        # Предварительная фильтрация через кэш
        if self.cache:
            candidates = self._filter_cached(user_context, candidates)
        
        # Формирование промпта
        prompt = self._build_ranking_prompt(user_context, candidates)
        
        # LLM-ранжирование
        response = self.llm.generate(prompt)
        ranked_items = self._parse_ranking(response)
        
        return ranked_items[:top_k]
    
    def _build_ranking_prompt(self, user_context, candidates):
        """Создание промпта для ранжирования"""
        return f"""
        Пользователь: {user_context['profile']}
        История: {user_context['history']}
        Контекст сессии: {user_context['session']}
        
        Кандидаты для ранжирования:
        {self._format_candidates(candidates)}
        
        Отранжируй кандидаты по релевантности (от наиболее к наименее):
        """
```

### Оптимизация производительности

1. **Кэширование**:
   - Кэширование результатов для популярных запросов
   - Предвычисление эмбеддингов предметов

2. **Модельная оптимизация**:
   - Использование более легких моделей (GPT-4o-mini, LLaMA-3-8B)
   - Квантование моделей (INT8, INT4)
   - Дистилляция в меньшую модель

3. **Архитектурная оптимизация**:
   - Двухэтапное ранжирование (быстрый фильтр → LLM)
   - Параллельная обработка батчами
   - Асинхронный инференс

### Метрики успеха

- **Latency**: P50, P95, P99 время ответа
- **Качество**: NDCG@10, MRR, HitRate
- **Бизнес-метрики**: CTR, конверсия, средний чек

### Преимущества

- ✅ Учет сложного контекста и нюансов
- ✅ Лучшая персонализация
- ✅ Возможность объяснения ранжирования

### Риски и ограничения

- ⚠️ Высокая latency для онлайн-инференса
- ⚠️ Стоимость LLM API при большом трафике
- ⚠️ Нестабильность результатов (temperature)

### Подходы

#### 5.1 Агент-ориентированный подход

- LLM как агент с инструментами (ReAct, AgentLLM)
- Планирование и выполнение многошаговых задач
- Саморефлексия и улучшение (Self-Refine, ReAcc)

#### 5.2 Генеративные рекомендации

- Прямая генерация ID предметов (P5, TIGER)
- Генерация через семантические токены (OneRec, OpenOneRec)
- Itemic tokenization для иерархического представления

#### 5.3 Гибридный подход (RecGPT)

- LLM для извлечения интересов
- LLM для генерации тегов
- Традиционная модель для финального ранжирования

### Техническая реализация

```python
class LLMRecommendationAgent:
    def __init__(self, llm_model="gpt-4o"):
        self.llm = LLMClient(model=llm_model)
        self.tools = {
            'get_user_profile': UserProfileService(),
            'get_candidates': CandidateGenerator(),
            'rank_items': ItemRanker(),
            'get_explanations': ExplanationGenerator()
        }
    
    def recommend(self, user_id, context, n_results=10):
        """Генерация рекомендаций через агент"""
        # Шаг 1: Получение контекста
        user_profile = self.tools['get_user_profile'].get(user_id)
        
        # Шаг 2: Планирование
        plan = self._create_plan(user_profile, context)
        
        # Шаг 3: Выполнение
        candidates = self.tools['get_candidates'].generate(user_id, n=100)
        ranked = self.tools['rank_items'].rank(user_profile, candidates)
        
        # Шаг 4: Генерация объяснений
        explanations = self.tools['get_explanations'].generate(
            user_profile, ranked[:n_results]
        )
        
        return {
            'recommendations': ranked[:n_results],
            'explanations': explanations,
            'reasoning_trace': self._get_reasoning_trace()
        }
    
    def _create_plan(self, user_profile, context):
        """Создание плана выполнения"""
        prompt = f"""
        Пользователь: {user_profile}
        Контекст: {context}
        
        Создай план для генерации рекомендаций:
        1. Какие данные нужны?
        2. Какие компоненты вызвать?
        3. Как объединить результаты?
        """
        return self.llm.generate(prompt)
```

### Метрики успеха

- **Качество**: NDCG@K, персонализация, разнообразие
- **Производительность**: Latency, throughput, стоимость
- **Объяснимость**: Качество объяснений (оценка пользователей)
- **Бизнес-метрики**: CTR, конверсия, удержание

### Преимущества

- ✅ Максимальная гибкость и адаптивность
- ✅ Естественные объяснения рекомендаций
- ✅ Возможность диалогового взаимодействия
- ✅ Интеграция внешних знаний

### Риски и ограничения

- ⚠️ Высокая сложность отладки
- ⚠️ Значительные вычислительные затраты
- ⚠️ Нестабильность результатов
- ⚠️ Сложность обеспечения консистентности

## Рекомендации по внедрению

### Для старта

1. **Начните с Итерации 1** - минимальный риск, быстрая ценность
2. **Параллельно запускайте Итерацию 2** - улучшение данных
3. **Переходите к Итерации 3** после накопления опыта

### Для production

1. **Тщательное тестирование** каждой итерации перед внедрением
2. **Постепенный rollout** (1% → 5% → 25% → 50% → 100%)
3. **Мониторинг** ключевых метрик на каждом этапе
4. **План отката** для каждой итерации

### Оптимизация затрат

1. **Кэширование** результатов LLM
2. **Batch processing** для офлайн-задач
3. **Модельная селекция** (дешевые модели для простых задач)
4. **Дистилляция** в меньшие модели после обучения
