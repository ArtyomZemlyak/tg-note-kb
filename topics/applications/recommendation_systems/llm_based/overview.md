# Обзор применения LLM в рекомендательных системах

## Что изменилось в 2024-2026

LLM в рекомендациях перестали быть только интерфейсом "чат + выдача". Текущий тренд - использовать их как отдельные модули внутри привычного RecSys-пайплайна (retrieval -> ranking -> re-ranking -> serving), а затем постепенно переходить к более генеративным и агентным схемам там, где это экономически оправдано.

Ключевой сдвиг: вместо вопроса "заменить ли весь стек LLM-ом?" команды чаще решают "на каком именно этапе LLM дает максимальный прирост при приемлемой латентности и стоимости?".

## Основные подходы (по месту в пайплайне)

### 1) LLM для инженерии признаков (наименее рискованный старт)

LLM используется офлайн для улучшения входных данных:
- генерация и нормализация тегов;
- суммаризация интересов пользователя из истории;
- извлечение атрибутов из текста, отзывов, карточек товара;
- построение richer metadata для long-tail айтемов.

Когда применять: есть слабые текстовые признаки, cold-start по новым айтемам, ограничение на изменения онлайн-латентности.

### 2) LLM как энкодер (семантические embeddings)

LLM/PLM формирует эмбеддинги пользователя и/или айтема, которые затем потребляются классическим retrieval/ranking.
- работает как "семантический слой" над существующим стеком;
- часто усиливает matching по тексту и мультимодальным описаниям;
- может использоваться в кросс-доменных сценариях.

Когда применять: нужна лучшая семантика без полного рефакторинга архитектуры.

### 3) LLM для генерации кандидатов (generative retrieval)

Подходы:
- генерация ID/semantic ID следующих релевантных айтемов;
- генерация кандидатов по истории сессии (autoregressive / sequence modeling);
- гибрид: LLM генерирует shortlist, ANN/классический retriever добавляет recall.

Плюс: может лучше работать с редкими паттернами интересов.  
Минус: сложнее контролировать покрытие каталога и стабильность в online.

Когда применять: большой каталог, заметный выигрыш от sequence/generative modeling, есть зрелая инфраструктура валидации.

### 4) LLM для ранжирования и re-ranking

LLM оценивает кандидатов с учетом богатого контекста:
- pointwise/pairwise/listwise scoring;
- контекст сессии, intent, constraints, business rules;
- генерация explainable rationale для internal audit или UX.

Обычно используется как "умный финальный слой" на ограниченном top-N (например, 50-200 кандидатов), чтобы держать латентность под контролем.

### 5) LLM для диалоговой и интерактивной рекомендации

LLM:
- уточняет предпочтения в диалоге;
- задает disambiguation-вопросы;
- объединяет retrieval + reasoning + explanation в одном UX-контуре.

Когда применять: discovery-сценарии (медиа, e-commerce, travel), где пользователь формулирует цели естественным языком.

### 6) LLM как оркестратор пайплайна (agentic recsys)

LLM не обязательно выбирает сами айтемы, но управляет шагами:
- выбирает стратегию retrieval/ranking;
- вызывает инструменты (feature store, rules engine, inventory, policy checks);
- формирует ответ и объяснение под канал/контекст.

Это сильный паттерн для сложных продуктовых сценариев, но требует жестких guardrails и observability.

## Архитектурные паттерны внедрения

### Pattern A: "LLM-augmentation" (рекомендуемый старт)

LLM добавляется в существующую систему точечно:
- офлайн enrichment;
- embedding generation;
- ограниченный re-rank.

Плюсы: низкий риск, быстрый rollout, простой rollback.

### Pattern B: "Hybrid stack"

Классический retrieval + LLM на late-stage задачах:
- кандидатогенерация остается дешевой и стабильной;
- LLM используется там, где контекст/объяснимость реально важны.

Плюсы: лучший баланс качество/стоимость.

### Pattern C: "End-to-end generative recommendation"

Модель авторегрессионно генерирует рекомендации (ID, semantic IDs, токены).

Плюсы: единая модель и унификация задач.  
Минусы: требования к данным, дебагу, latency, безопасному деплою.

## Что сейчас считается best practice

- Начинать с офлайн и near-line сценариев, где LLM не критичен к P95 latency.
- Делать staged rollout: shadow -> small traffic -> progressive ramp.
- Выделять budget на инференс и считать uplift на единицу стоимости.
- Держать deterministic слой правил поверх LLM (policy, availability, business constraints).
- Комбинировать fine-tuning и retrieval-обновления: model refresh не покрывает быстрый drift интересов.
- Логировать reasoning traces/промпты/версии моделей для воспроизводимости и дебага.

## Ключевые метрики оценки подходов

### Offline
- NDCG@K, Recall@K, MRR, HitRate;
- coverage, novelty, diversity, serendipity;
- качество объяснений (human eval / LLM-as-judge с ручной валидацией).

### Online
- CTR, CVR, GMV/Watch Time/Retention;
- latency (P50/P95/P99), error rate, timeout rate;
- стоимость на 1k рекомендаций и cost-per-uplift.

### Надежность и безопасность
- устойчивость к prompt injection в tool-цепочках;
- токсичность/галлюцинации в объяснениях;
- bias/fairness по сегментам;
- privacy leakage и соответствие policy/consent.

## Ограничения и риски

- Высокая стоимость и вариативность качества при больших объемах трафика.
- Нестабильность ответов при нефиксированных параметрах генерации.
- Сложность гарантировать строгие бизнес-ограничения без rule layer.
- Ухудшение в "быстрых" сценариях без грамотного кеширования и батчинга.
- Сложность наблюдаемости: без хорошего логирования тяжело объяснить деградации.

## Практический выбор подхода (краткий decision guide)

- Нужен быстрый и безопасный старт -> `Feature engineering` + `LLM-encoder`.
- Нужна точнее персонализация без взрыва latency -> `Hybrid stack` + `LLM re-rank top-N`.
- Нужен conversational UX -> `Dialogue + tool-augmented orchestration`.
- Нужен research-level прорыв в sequence recommendation -> `Generative retrieval / end-to-end`, но только с сильной MLOps и экспериментальной дисциплиной.
