# Обучение эмбеддингов GitHub репозиториев для поиска схожих репозиториев

## Краткое описание

Проект по созданию эмбеддингов GitHub репозиториев с использованием GitHub Stars как сигнала для понимания семантической близости репозиториев. Основная цель - построить систему рекомендаций для репозиториев и возможность сравнения профилей разработчиков на основе их интересов и поведения на GitHub.

## Основные концепции

### Гипотеза кластеризации
Схожие элементы часто появляются в схожих контекстах. В контексте проекта это означает создание эмбеддинг-пространства, где семантически схожие репозитории находятся близко друг к другу. В этом пространстве могут формироваться оси, представляющие измерения типа "Данные (подготовка и анализ) vs Модели (обучение и инференс)" и "Локальная/одноузловая vs Big Data/кластерная вычислительная среда", хотя на практике нейронные сети автоматически обучаются этим измерениям.

## Источники сигналов и подготовка данных

### Текстовые данные
- **Источник**: README.md файлы репозиториев
- **Использование**: Инициализация с использованием модели Qwen3-Embedding-0.6B с поддержкой MRL (Matryoshka Representation Learning)
- **Процессинг**: Сохранение только первых 128D наиболее важных компонентов эмбеддингов

### Матрица звёзд (Stars Matrix)
- **Использование**: Основное обучение через collaborative filtering, используя паттерны того, какие репозитории пользователи отмечают вместе
- **Источник**: GitHub Archive dataset в BigQuery (приблизительно 1 ТБ необработанных данных)
- **Запросы**:
  1. Stars (WatchEvent): Сбор пользователей с 10-800 звёзд (фильтрация неактивных пользователей и ботов), сохранение порядка звёзд
  2. Meta (PushEvent): Сбор названий репозиториев, дат коммитов и описаний
- **Результат**: Parquet файл с 4 миллионами разработчиков и 2.5 миллионами уникальных репозиториев

## Архитектура машинного обучения

### Модель
- **Используемая модель**: `torch.nn.EmbeddingBag` - по сути, большая таблица, отображающая `repo_id -> vector[128]`, которая эффективно агрегирует (усредняет) векторы
- **Цель**: Создать легковесное решение, подходящее для развертывания в браузере
- **Обоснование**: Трансформированные модели были исключены из рассмотрения по причинам производительности

### Выборка и функция потерь
Подход использует collaborative filtering с рандомным разделением выборки:

1. **Основной метод**: Разделение списка звёзд каждого пользователя на две случайные, непересекающиеся группы
2. **Цель обучения**:
   - Сближение групп из одного пользователя
   - Отдаление групп из разных пользователей

Реализация показала, что удивительно, простое случайное разделение работало лучше, чем сложные временные подходы типа Word2Vec sliding windows или hard negative miners.

### Функция потерь
- **Основной выбор**: MultiSimilarityLoss из библиотеки pytorch-metric-learning
- **Подход**: Metric Learning (вместо графовых алгоритмов типа LightGCN или факторизации матриц)
- **Преимущества**: Требует меньше ресурсов GPU и предоставляет гибкость в управлении эмбеддинг-пространством

## Оценка качества

### Метод Ground Truth
- **Подход**: Использование "Awesome Lists" (например, "Awesome Python", "Awesome React") как курируемых, модерируемых человеком кластеров схожих библиотек
- **Процесс**: Загрузка README файлов из этих списков, идентификация совместных вхождений, взвешивание силы соединения и использование метрики NDCG (Normalized Discounted Cumulative Gain) для оценки ранжирования
- **Цель**: Позволило честное сравнение различных функций потерь, гиперпараметров и методов выборки

## Техническая реализация

### Архитектура фронтенда
1. **Данные**: Клиент загружает сжатые эмбеддинги (FP16, ~80MB) и метаданные, кэшируемые в IndexedDB
2. **Поиск**: Использование библиотеки USearch с ядром, скомпилированным в WebAssembly, для векторного поиска
3. **Технология**: Демонстрация только на клиенте без серверной стороны

### Низкоуровневые оптимизации
- **Вызов**: HNSW индекс требовал больше памяти, чем сырые эмбеддинги
- **Решение**: Реализация точного поиска (Exact Search) с использованием WASM
- **Техники**: Использование низкоуровневых методов `_usearch_exact_search`, ручное управление памятью через `_malloc`, манипуляции с указателями
- **Конвертация**: Реализация конвертации FP16 в FP32 "на лету" в браузере из-за ограниченной нативной поддержки FP16
- **Производительность**: Достигнут быстрый поиск по 300k+ векторам без использования индексов HNSW

## Результаты и находки

### Что не сработало
- **Векторная арифметика**: Ожидаемые NLP-стилевые арифметические операции (как "King - Man + Woman = Queen") не сработали с эмбеддингами репозиториев
- **Гипотеза**: Pandas - Python + TypeScript = Danfo.js не поддерживалась эмбеддинг-пространством
- **Кластеризация**: Ожидаемая чёткая кластерная структура не была чётко видна

### Что сработало
- **Семантический поиск**: Успешно находит альтернативные библиотеки, которые семантически релевантны, но могут быть неизвестны пользователю
- **Снижение смещения**: В отличие от LLM, которые часто склоняются к популярным решениям, этот подход, основанный на поведении ИТ-специалистов, раскрывает:
  1. Нишевые инструменты, используемые профилями, но не часто упоминаемые в блогах
  2. Новые решения, которые набрали популярность с похожими "шаблонами отмечания"
  3. Локальное выполнение функций на клиентских устройствах
- **Практическая ценность**: Достигнута основная цель по нахождению семантически релевантных альтернатив

## Ключевые технические детали

- **Размерность эмбеддингов**: 128-мерные векторы
- **Масштаб репозиториев**: 300k+ репозиториев с обученными эмбеддингами
- **Масштаб пользователей**: 4 миллиона разработчиков в матрице интересов
- **Метод машинного обучения**: Metric Learning с EmbeddingBag и MultiSimilarityLoss
- **Развертывание**: WASM-реализация на стороне клиента для векторного поиска (KNN) в браузере
- **Улучшение качества**: Текстовая инициализация (элементы README) добавила ~10% улучшения в финальное качество

## Значение и выводы

Проект демонстрирует, что традиционные подходы к созданию эмбеддингов остаются ценными в эпоху GenAI, предоставляя персонализированные рекомендации, основанные на реальных паттернах поведения разработчиков вместо популярности или смещений LLM.
